SECTION 4 - TICK SYSTEM (white single / white double / pink double)
------------------------------------------------
States were already server-driven; this window closed the loop:
4.1  Visuals: SENT single tick grey -> white (onPrimary); DELIVERED double
  grey -> white; READ double blue -> pink #F06292 (centralized ReadPink).
  Privacy label "blue ticks" -> "pink ticks".
4.2  Pipeline (verified end-to-end in code): send->ack SENT (receiver offline
  stays single); peer app auto-sends receipt.delivered on arrival ->
  DELIVERED; peer opens chat -> receipt.read -> READ. Monotonic rank guard:
  repeats/out-of-order frames never downgrade or duplicate.
4.3  NEW data/local/MessageStatusStore.kt: DataStore rank cache (cap 2000),
  saved on every SENT/DELIVERED/READ change, merged max-rank-wins at startup
  (pure mergeRanks, unit-tested) - ticks survive restarts, no flash-back.
  SENDING/FAILED stay transient by design.
4.4  Reconnect catch-up: history loads now also send markDelivered for the 20
  most-recent peer messages (plus existing markRead of latest) - the other
  side's pending single ticks upgrade without refresh. Uniform across
  text/image/voice/docs (status keyed by message id, shared footer).
4.5  Boundary (honest): receiver-side SENT->DELIVERED on YOUR screen needs the
  server to fan out the peer's sync receipts; anything the server emits is
  applied instantly. Stuck single tick with peer online = server gap, not client.
4.6  Tests: MessageStatusStoreTest 4 tests (merge ranks, upgrade/no-downgrade
  sequence, JSON round-trip).
